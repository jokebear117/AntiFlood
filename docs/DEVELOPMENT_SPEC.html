Anti-Flood
개발 명세서

강우 데이터가 순차적으로 입력될 때 서울의 근사 침수 수심을 갱신하고, 필요한 격자 계산만 수행해 멀티코어 CPU에서 결과를 시각화하는 로컬 시스템.

사용자 검수 전, 구현 승인 아님버전 0.92026.11.24기준: ARCHITECTURE.md, DECISIONS.md
현재 설계와 실행 방법

이 기록은 비교 기능을 추가하기 전의 초안이다. 서울 전역의 Reference 및 Streaming 계산과 비교는 시스템 아키텍처에, 실제 사용 방법은 설치와 실행에 기록한다.

01 목적과 최종 완료 기준

최종 사용자 경험은 하나다. 서울 지도를 열고 강우 시나리오를 재생하면, 시간이 흐름에 따라 계산된 침수 수심이 지도 위에서 변한다. 강우가 강해지거나 물이 이동하는 지역은 계산 대상으로 활성화된다. 계산은 노트북의 CPU 여러 코어에서 실행된다.

완료되면 반드시 가능한 일

  • 실제 DEM과 강우 자료를 입력한다.
  • 지역별 배수 조건을 수심 계산에 반영한다.
  • 이전 수심을 유지하면서 다음 강우 시각으로 진행한다.
  • 100m Tile 활성화 상태가 실제 계산 대상에 반영된다.
  • 브라우저의 3D 지도에서 수심과 시각을 확인한다.
  • 모든 핵심 기능을 로컬에서 재현할 수 있다.

이번 프로젝트에서 하지 않는 일

  • 새 유체 역학 알고리즘 발명
  • Landlab, ANUGA, WCA2D 비교 연구
  • 도시 재난 운영용 실시간 경보
  • 새로운 분산 클러스터 구축
  • 성능 평가 플랫폼과 복잡한 대시보드
  • 미래 강우 예측, 대피 경로, 시민 계정
완료 판정의 기준

시작 버튼을 누를 수 있는 웹페이지가 아니라, 실제 입력에서 계산된 수심이 시간에 따라 변하고 그 계산의 출처와 시각을 확인할 수 있는 실행 가능한 시스템이어야 한다. 가짜 수심 데이터나 미리 그려 놓은 침수 이미지로 대신할 수 없다.

03 전체 아키텍처와 데이터 흐름

Data Layer서울 DEM, 강우 시계열, 배수 조건을 동일 좌표 및 단위로 정렬
↓
Stream Processor현재 시각의 강우 입력, 60분 누적량, 최근 강우 점수 유지
↓
Flood Simulation EngineTile 활성화, 연속 수심 상태, WCA2D 계열 물 이동, OpenMP 병렬 처리
↓
결과 전달 (FastAPI)최신 상태, 결과 PNG, 시각, 데이터 출처 제공
↓
Visualization서울 3D 지형, 수심 색상, 재생과 일시정지

단일 상태 소유자 원칙: 수심 배열과 계산 시각은 CA 엔진이 관리한다. Python은 입력과 실행을 제어하고, API와 브라우저는 결과만 읽는다. 프런트엔드나 Solar가 수심을 독자적으로 계산하지 않는다.

처리 순서: 입력 검증 → 강우 이벤트 반영 → 활성 영역 갱신 → 인접 셀 간 유량 계산 → 수심 갱신 → 스냅샷 저장 → 화면 반영. 수치 계산 내부의 정확한 연산 순서는 채택한 CA 모델이 요구하는 규칙을 따른다.

04 데이터 계약

원본 파일은 리포지토리의 기존 Dataset/ 폴더에서 읽는다. Codex는 먼저 실제 파일명과 컬럼, 좌표계, 관측 시간 간격을 확인하고 그 내용을 매핑한다. 가상의 파일이나 관측값을 있는 것처럼 생성하면 안 된다.

4.1 필수 입력

입력필수 정보기준 단위누락 시
DEM격자 고도, CRS, 픽셀 크기, NoData, 출처표고 m, 수평 좌표 m실행 중단. 임의 지형으로 대체 금지
강우관측 시각, 지역 또는 위치, 구간 강우량, 시간 간격mm/구간 입력, 내부 m/s실행 중단. 실제 자료가 없으면 입력 미구비로 보고
배수지역별 유효 배수량 또는 명시적 가정내부 m/s 등가 수심 감소율명시적 기본값 사용 가능, 가정임을 기록

4.2 표준 내부 데이터 구조

GridData:
  elevation_m: float32[rows, cols]
  valid_mask: bool[rows, cols]
  crs: string
  transform: 6-element affine transform
  cell_area_m2: float or float32[rows, cols]
  drainage_m_per_s: float32[rows, cols]
  drainage_source: "observed" | "assumed" | "mixed"

RainEvent:
  event_time_utc: ISO-8601 string
  interval_start_utc: ISO-8601 string
  interval_end_utc: ISO-8601 string
  region_id: string
  rainfall_depth_mm: nonnegative float
  source_id: string

Snapshot:
  simulated_time_utc: ISO-8601 string
  depth_m: float32[rows, cols]
  active_tile_ids: list[string]
  input_source_ids: list[string]
  total_water_m3: float
  status: "computed"

위 구조는 Anti-Flood 내부 계약이다. 실제 공개 엔진의 원본 CSV 구조를 이 형식이라고 가정하지 않는다. 데이터 어댑터가 두 형식을 변환한다.

4.3 시간과 단위

  • 강우 구간은 [interval_start, interval_end)로 해석한다. 동일 관측이 중복 적용되지 않도록 한다.
  • 모든 저장 및 API 시각은 UTC ISO 8601로 통일하고, UI에서는 한국 시간으로 표시한다.
  • 구간 강우량 mm는 해당 구간 전체에서만 유효하다. 계산 시간 단계가 더 짧다면 구간 내 강우 강도가 일정하다고 가정해 분배하고 이 가정을 명시한다.
  • 강우 강도 변환은 mm/h ÷ 3,600,000 = m/s로 한다.
  • 배수 조건의 단위가 면적당 유량으로 정의되지 않았다면 바로 수심 감소량에 더하지 않는다. 단위와 의미를 먼저 변환한다.

4.4 공간 정합성

  • DEM은 미터 단위 투영 CRS를 사용한다. 실제 소스 CRS를 읽고 필요한 경우 명시적으로 변환한다.
  • 강우 관측소와 행정구역 단위 자료는 실제 공간 매핑 정보가 있을 때만 격자에 배정한다.
  • 빈 관측 영역에 임의 값을 넣지 않는다. 공간 보간을 채택해야 하는 경우 그 방법과 불확실성을 설정 파일과 UI에 표시한다.
  • 수직 기준이 미확인된 표고를 다른 수직 기준의 자료와 혼합하지 않는다.
  • 유효하지 않은 지형 셀은 경계 규칙으로 처리하며 정상 지형처럼 계산하지 않는다.
실데이터 기준의 개발

소형 합성 데이터는 엔진 빌드와 최소 동작 점검에만 사용할 수 있다. 최종 시연과 지도에 표시되는 수심은 확보된 실제 서울 DEM과 강우 입력에서 계산한 결과여야 한다. 데이터가 부족하면 해당 제약을 명확히 보고하고 멈춘다.

05 격자와 100m Tile 정의

5.1 서로 다른 두 공간 단위

구분정의사용처
물리 격자(Cell)원본 DEM과 일치하는 약 30m 래스터 셀고도, 수심, 유량 및 강우 반영
관리 Tile투영 좌표에서 100m × 100m 정사각형활성화, 스케줄링, UI 영역 표시

100m는 30m의 정수배가 아니므로 Tile을 정확히 3×3 또는 4×4 Cell로 만들지 않는다. 기존 Cell 격자를 분할하거나 보간하지 않고, 셀 중심점이 속하는 Tile에 관리상 소속시키는 방식을 사용한다.

tile_x = floor((cell_center_x - tile_origin_x) / 100.0)
tile_y = floor((cell_center_y - tile_origin_y) / 100.0)
tile_id = f"{tile_x}:{tile_y}"

Cell은 정확히 하나의 Tile에 속한다. Tile 경계를 넘어가는 물의 흐름은 기존 Cell의 이웃 관계를 통해 계산한다. Tile 경계에서 유량이 막히거나 두 번 적용되면 안 된다.

5.2 계산 영역

최종 시스템은 서울 전역의 공간 데이터를 로딩할 수 있는 구조를 목표로 한다. 그러나 계산 대상이 너무 커서 노트북 메모리나 실행 시간이 한계를 넘으면, 동일한 파이프라인에서 서울의 지정된 영역을 선택 실행할 수 있어야 한다. UI는 선택된 분석 범위를 명확히 표시하고 서울 전역을 실시간 계산한 것처럼 표현하지 않는다.

06 CA 계산 엔진과 물리 상태 계약

6.1 재사용할 코드의 우선순위

1순위는 공개 저장소 FluiditLtd/caddies-caflood의 WCA2D 계열 계산 코드다. 이 저장소는 원본 Exeter CADDIES를 기반으로 하며, README에 셀별 시간 가변 강우, OpenMP, 초기 수심, 일부 공간별 물리 계수를 지원한다고 설명한다. 원본 CADDIES 기본 버전과 포크의 기능은 혼동하지 않는다.

공식 Exeter 자료는 CADDIES 프로젝트 페이지를 참조한다. 포크 README는 GPL-2.0을 명시하지만 원본 사이트에는 다른 라이선스 설명도 있으므로, 실제로 가져오는 소스 트리의 LICENSE와 하위 의존성을 각각 확인하고 출처 및 수정 내용을 보존한다.

재사용 가능하다고 확인된 기능과 그렇지 않은 기능

공개 README 수준에서 OpenMP와 지역별 시간 가변 강우 지원은 확인된다. 반면 외부에서 활성 Tile만 선택적으로 계산하도록 지정하고, 새 강우를 스트림으로 계속 주입하는 인터페이스는 아직 보장되지 않는다. 엔진의 인터페이스가 지원하지 않는 기능을 이미 구현된 것처럼 적지 않는다.

6.2 엔진 어댑터의 필수 기능

아래 메서드는 Anti-Flood의 요구 계약이지, WCA2D가 원래 제공하는 API 이름이 아니다. 실제 코드를 읽은 뒤 C++ 연동, 명령 프로토콜, 파일 기반 체크포인트 가운데 한 가지 방법으로 구현한다.

SimulationSession
  initialize(GridData, initial_time, settings) -> void
  set_rain(interval_start, interval_end, rain_grid_m_per_s) -> void
  advance_to(target_time) -> void
  get_depth() -> float32[rows, cols]
  get_simulated_time() -> timestamp
  get_active_tiles() -> list[tile_id]
  close() -> void

advance_to()는 현재 시뮬레이션 상태에서 앞으로만 계산한다. 다음 강우가 들어올 때 이전 계산 결과를 초기화하지 않는다. 저장된 현재 수심, 인접 유량에 필요한 상태, 계산 시각이 연속적으로 이어져야 한다.

6.3 기본 물리 제약

개념적으로 각 Cell의 물 부피 변화는 강우 유입 + 주변 유입 - 배수 및 주변 유출이다. 실제 이웃 간 유량과 내부 시간 간격은 채택한 WCA2D 계산 규칙으로 결정한다.

depth_next = depth_previous
           + rainfall_depth
           - effective_drainage_depth
           + net_neighbor_flow_volume / cell_area
  • 수심은 음수가 될 수 없다. 물이 부족한 셀에서 배수량이나 유출량을 기존 물보다 크게 빼지 않는다.
  • 인접 Cell 간 물의 이동은 전체 시스템에서 한 번 유출된 양이 다른 Cell에 한 번 유입되도록 처리한다.
  • 시뮬레이션 외곽 경계의 유출은 별도 기록한다. 열린 경계와 닫힌 경계를 혼동하지 않는다.
  • 강우, 실제 또는 가정 배수, 경계 유출을 구분해 누적한다.
  • 물리 엔진의 CFL 조건이나 적응형 시간 간격을 무시하고 임의의 고정 Δt를 강제하지 않는다.

6.4 배수 모델의 범위

지역별 배수능력은 도시 하수관망의 상세 모의가 아니라 유효 수심 감소율로 단순화한다. 실제 자료가 있으면 단위와 공간 범위를 맞추어 적용한다. 자료가 부족할 경우 단일 기본값이나 구역별 가정값을 사용하고 반드시 assumed로 표시한다. 침투와 하수 배수는 물리적으로 다른 현상이므로 엔진의 침투 파라미터를 그대로 하수 배수량이라고 명명하지 않는다.

07 강우 스트림 처리 계약

7.1 시간순 재생

Data Layer가 준비한 강우 이벤트를 이벤트 시각 순서대로 처리한다. 새 이벤트를 적용하기 전에 해당 이벤트보다 미래에 발생할 강우를 Scheduler에 제공하지 않는다. 재생 속도는 UI 편의를 위한 기능이며, 실제 관측 시각과 시뮬레이션 시각을 뒤섞지 않는다.

7.2 지역별 상태

RegionRainState:
  current_intensity_mm_per_h: float
  rolling_60min_mm: float
  decayed_rain_score: float
  last_event_time_utc: timestamp
  • Sliding Window는 해당 지역의 최근 60분 정확한 누적 강우량을 유지한다. 시각 및 구간 길이가 달라도 교집합 시간에 따라 누적한다.
  • 지수 감쇠 점수는 S_new = lambda * S_old + r_new의 형태로 갱신한다. 초기 lambda = 0.8은 의사결정 점수의 시작 설정이며 물리 모형 계수가 아니다.
  • 감쇠 점수에 사용할 강우 입력은 동일 길이의 집계 구간으로 정규화한다. 이벤트 간격이 불규칙하다면 경과 시간에 따른 감쇠를 적용한다.
  • 강우 원본 이력은 파일에 보존하지만, 운영 중 현재 상태 계산을 위해 전 구간을 반복 스캔하지 않는다.

7.3 이벤트 누락과 중복

동일 이벤트 식별자와 동일 관측 구간을 중복 적용하지 않는다. 강우가 없는 구간은 실제 0 관측이 있는 경우에만 0으로 취급한다. 관측 누락은 missing으로 남기고 0으로 치환하지 않는다. 누락을 메우지 않고 계산 가능한 구간만 실행하거나 사용자에게 오류를 알린다.

08 Tile 활성화와 계산 스케줄링

8.1 활성화는 단순히 폭우 임계값으로 결정하지 않는다

폭우가 새로 발생한 곳은 반드시 우선적으로 살펴본다. 다만 물은 비가 그친 지역으로도 흘러들기 때문에, 다음 중 한 가지에 해당하면 해당 Tile을 계산 대상으로 유지한다.

  1. 구간 강우가 0보다 크다.
  2. Tile 내부에 기준치 이상의 잔류 수심이 있다.
  3. 인접 Cell 또는 인접 Tile에서 물이 유입될 가능성이 있다.
  4. 계산 중인 다른 Cell에 영향을 주는 경계 Cell이 포함된다.

기본 습윤 판정값은 1 mm를 시작 설정으로 사용하되, WCA2D 내부의 wet/dry 임계값과 충돌하지 않도록 맞춘다. 판정값보다 작은 수심을 곧바로 0으로 지우지는 않는다.

8.2 물리 계산의 활성 범위

on_each_physical_step():
  rainfall_cells = cells_receiving_rain()
  wet_cells = cells_with_water_or_possible_flux()
  active_cells = rainfall_cells UNION wet_cells
  active_cells = active_cells UNION neighbors(active_cells)
  active_tiles = tiles_containing(active_cells)
  compute_flux_for_required_neighbors(active_cells)
  synchronize_flux_and_update_depth()
  refresh_active_set_after_movement()

이 의사코드는 선택적 계산의 의도를 설명한다. 실제 CA 엔진의 계산 커널을 정확히 읽은 뒤 연산 순서를 맞춘다. 활성 셀에 접한 비활성 셀로 들어가는 유량을 무시해서는 안 된다. 안전하게 처리할 수 없다면 해당 구간을 전체 격자 방식으로 계산해야 하며, 이것을 적응형 계산 성공으로 보고하지 않는다.

8.3 집중호우 우선순위

계산 영역이 많을 때 우선순위는 현재 강우 강도, 최근 누적 강우, 잔류 수심, 마지막 결과 시각을 바탕으로 정한다. 초기 집중호우 기준은 30 mm/h로 둔다. 이는 알고리즘 동작을 위한 임시 운영값이며, 실제 침수 위험 경보 기준이라고 주장하지 않는다.

한 물리 계산 시점에 필요한 모든 활성 셀은 경계 유량을 포함하여 계산해야 한다. 따라서 우선순위는 작업 순서와 결과 전달 순서에 주로 사용하며, 임의로 낮은 우선순위의 습윤 격자를 생략하는 수단으로 사용하지 않는다. 이 원칙이 지켜지지 않으면 물리 계산의 정확성이 깨진다.

8.4 결과 갱신 주기

지역 상태목표 결과 갱신 주기표시 주의점
강우와 수심 변화가 거의 없음60분마지막 실제 계산 시각 표시
약한 강우 지속30분시뮬레이션 계산 시각과 구분
강우량 증가10분입력 관측 주기보다 상세하게 추정한 경우 가정 표기
집중호우 또는 빠른 수심 변화5분결과가 지연되면 지연 상태 표시

이 주기는 화면과 스냅샷 제공 주기의 시작값이다. 물리 계산 시간 간격과 동일하지 않고, 이것만 변경해 물리 연산량이 줄었다고 주장할 수 없다. 5분 결과를 계산하는 데 실제로 5분 이상 걸릴 수 있으며, 이때는 지연을 숨기지 않는다.

09 CPU 병렬화와 상태 동기화

하나의 연속된 격자 수심 상태를 하나의 CA 엔진이 소유한다. 엔진이 지원하는 OpenMP 공유 메모리 병렬화를 사용한다. Python에서 Tile마다 별도 프로세스를 시작하거나 OpenMP 위에 추가 프로세스 풀을 겹쳐 실행하지 않는다.

  • 기본 실행은 노트북 CPU의 4개 스레드로 시작하며 환경 변수 또는 설정으로 변경 가능하게 한다.
  • 같은 Cell을 동시에 여러 스레드가 갱신하지 않도록 한다.
  • 인접 유량 계산과 수심 반영 사이의 동기화 지점은 엔진의 기존 알고리즘을 따른다.
  • 결과 스냅샷은 한 물리 시각의 계산이 끝난 뒤에만 생성한다. 일부 셀이 과거 상태이고 일부가 미래 상태인 결과를 저장하지 않는다.
  • 다중 노드 네트워크, MPI, Kubernetes는 구현하지 않는다. 발표에서도 실제 분산 클러스터라고 말하지 않는다.

MapReduce는 강우 데이터의 지역별 분할과 집계 개념을 설명하는 데 사용하되, 작은 입력을 처리하기 위해 Hadoop이나 Spark를 설치하지 않는다. 구현은 Python의 단순한 파티셔닝과 증분 집계로 충분하다.

10.3 오류 원칙

필수 입력 데이터가 없거나, 좌표계가 유효하지 않거나, 엔진 실행이 실패하면 어느 단계가 실패했는지 구체적인 오류를 반환한다. 실패를 무시하고 빈 수심 이미지를 정상 결과로 반환하지 않는다. 모든 API 키는 서버 환경 변수로만 관리한다.

11 사용자 화면 명세

화면은 지도 하나와 작은 제어 패널 하나로 구성한다. 지도 영역을 중심으로 두고 별도의 분석 대시보드는 만들지 않는다.

첫 구현에서는 수심 래스터를 PNG로 렌더링하고 공간 좌표 정보와 함께 제공한다. 필요한 범위의 재투영과 투명 마스크를 적용한다. 지형 타일 및 지도 배경은 이용 조건이 확인된 출처를 선택한다. 서울 S-MAP의 비공개 내부 기능은 사용하지 않는다.

강의 프로젝트의 LLM 에이전트 요구사항을 위한 최소 기능이다. Solar는 모델링 결과를 재계산하거나 변경하지 않는다. 현재 실행 상태를 도구로 읽고 자연어로 설명한다.

13 실행 환경, 산출물, 보존 원칙

13.1 기준 환경

  • Windows 기반 노트북의 CPU 실행을 기준으로 한다. WSL 사용은 기존 엔진의 빌드 조건에 맞게 선택한다.
  • Python 3.11, FastAPI, NumPy, Rasterio를 사용한다. C++ 소스의 빌드 체인은 선택한 공개 코드의 요구사항에 맞춘다.
  • 기본 OpenMP 스레드 수는 4다. 한 번에 하나의 시뮬레이션 세션을 실행한다.
  • 노트북에서 전체 서울을 한 번에 계산하기 어렵다면 분석 범위를 지정해 같은 기능을 실행한다. 실제 계산 범위를 UI에 표시한다.

13.2 저장할 산출물

산출물이유저장 방식

원본 데이터는 변경하지 않는다. 생성된 프레임과 로그는 원본 Dataset/과 분리하여 저장하고 버전 관리에서 제외한다. 캐시를 지워도 원본 데이터로 다시 생성할 수 있어야 한다. 프로젝트의 최종 폴더 구조는 별도 5단계에서 확정한다.

14 구현 순서와 단계별 통과 조건

다음 순서를 바꾸지 않는다. 각 단계는 작동하는 코드와 눈으로 확인 가능한 실행 결과를 남겨야 한다. 특정 단계가 막혔다고 다음 화면을 가짜 결과로 먼저 완성하지 않는다.

M0
입력과 코드 출처를 실제로 확인

작업: 현재 리포지토리와 Dataset/을 읽는다. DEM 및 강우와 배수 파일의 실제 구조를 기록한다. 위에서 명시한 CAFLOOD 포크와 하위 CADDIES API의 소스, 빌드 방법, 라이선스를 확인한다.

완료: 사용 가능한 파일과 없는 파일을 명확하게 식별하고, 어떤 실제 소스와 브랜치를 사용할지 확정할 수 있다. 아직 기능을 만들어 냈다고 보고하지 않는다.

M1
CA 엔진을 실제로 실행하고 수심 배열을 읽는다

작업: 공개 엔진을 로컬에서 빌드하거나 제공된 호환 실행 파일로 실행한다. 소형 입력에서 강우가 수심 변화를 발생시키는지 확인하고 출력 배열을 Python에서 읽는다. 연속 상태 갱신과 계산 마스크 연결 가능 지점을 소스에서 확인한다.

완료: 실수심 배열을 파일 또는 API로 받는다. 두 핵심 연동 기능이 불가능하면 정확한 원인과 최소 수정 지점만 보고하고 멈춘다. 승인 없이 다른 유체 엔진으로 전환하지 않는다.

M2
서울 지형, 강우, 배수 입력을 연결한다

작업: 기존 데이터셋을 공통 격자로 정렬하고, 강우 이벤트를 시간순으로 주입한다. 배수는 출처가 있는 자료 또는 표시된 가정값만 적용한다.

완료: 실제 지형에서 연속된 두 시각 이상의 수심 상태가 생성된다. 관측 시각과 단위가 확인 가능하다.

M3
Tile 활성화와 CPU 병렬화

작업: 100m Tile 소속을 생성하고 강우, 수심, 인접 유량을 이용해 활성 영역을 갱신한다. 엔진의 계산 커널에 실제 활성 마스크를 연결한다. CPU OpenMP를 사용한다.

완료: Tile 활성 여부가 계산 루프에 반영되고, 인접 Tile의 물 이동이 유지된다. 계산 생략이 불가능한 경우 결과 전송 최적화로 대체했다고 주장하지 않는다.

M4
FastAPI와 서울 3D 지도 연결

작업: 최신 상태, 재생 제어, 수심 PNG를 API로 제공한다. MapLibre에서 수심이 해당 위치에 표시되도록 연결한다.

완료: 재생, 일시정지, 재개, 초기화가 동작하고 수심과 마지막 계산 시각이 지도에 반영된다.

M5
Solar 보조 기능과 최종 실행 경로

작업: 조회 전용 두 도구와 Solar 호출을 연결한다. 설치 및 실행 명령을 명시한다. 핵심 기능이 키 없이도 실행되는지 확인한다.

완료: 깨끗한 로컬 실행 환경에서 정해진 절차로 시뮬레이션을 시작하고 계산된 수심을 3D 지도에서 확인할 수 있다. Solar가 제공되면 현재 상태를 물을 수 있다.

15 최소 동작 점검만 수행

별도의 비교 실험 플랫폼, 파라미터 탐색, 성능 벤치마크 자동화는 만들지 않는다. 아래는 시스템이 잘못된 수심을 계산하거나 실행되지 않는 문제를 막기 위한 최소 점검이다.

  • 강우와 초기 수심이 0이면 닫힌 영역의 수심이 증가하지 않는다.
  • 강우가 유입되면 물 부피가 해당 유입량만큼 증가하며, 배수와 경계 유출이 있으면 그 양이 반영된다.
  • 모든 유효 Cell의 수심이 음수가 아니며 NaN 또는 무한대가 발생하지 않는다.
  • 인접 Tile 사이에 물이 이동할 수 있으며, Tile 경계에서 물이 사라지거나 중복되지 않는다.
  • 연속 강우 구간을 적용할 때 수심이 매번 초기화되지 않는다.
  • 일시정지 후에는 시뮬레이션 시각이 진행하지 않으며, 재개하면 이전 상태에서 이어진다.
  • API의 수심 프레임과 UI에 표시한 계산 시각이 일치한다.

수량 보존 점검에는 입력과 출력의 반올림 및 계산 오차를 고려한 작은 수치 허용오차를 쓴다. 그 허용오차는 실제 사용한 계산 정밀도와 엔진 설정을 바탕으로 정하고 기록한다. 오류를 숨길 정도로 크게 설정하지 않는다.

점검 완료의 의미

이 점검을 통과했다고 서울의 실제 침수 깊이가 관측과 일치한다고 주장할 수 있는 것은 아니다. 구현된 프로그램이 최소한의 수학적 및 시스템적 제약을 지킨다는 의미다.

작업 원칙

작업 범위

  1. 이 명세와 ARCHITECTURE.md, DECISIONS.md를 우선한다. 충돌이 발견되면 추측해서 변경하지 말고 충돌 지점을 보고한다.
  2. 현재 마일스톤의 코드만 수정한다. 다음 마일스톤 기능을 미리 만들지 않는다.
  3. 새 웹 프레임워크, 메시지 브로커, DB, 클라우드 서비스, GPU 의존성, 유체 엔진을 임의로 추가하지 않는다.
  4. 프로젝트의 기존 데이터와 공개 엔진을 우선 재사용한다. 불필요한 래퍼 계층, 추상 클래스, 공통 프레임워크를 만들지 않는다.
  5. 실제 계산 없이 랜덤 수심, 하드코딩된 수심 배열, 가짜 성공 메시지를 사용해 기능 완료로 보고하지 않는다.

검증과 문서화

  1. 위 최소 동작 점검 외에 대규모 실험, 자동 튜닝, 수치모델 비교를 시작하지 않는다.
  2. 테스트가 실패하면 원인과 수정 범위를 확인해 실제 코드를 고친다. 테스트 코드를 늘리는 것으로 문제 해결을 대신하지 않는다.
  3. 사용자가 요청하지 않은 README 개편, 전체 폴더 재구성, 디자인 리뉴얼, 대규모 리팩터링을 하지 않는다.
  4. 문서는 구현된 동작만 기술한다. 예정된 기능을 완료된 것처럼 표시하지 않는다.
  5. 공개 코드 라이선스와 데이터 출처, 지형 및 배수 가정은 숨기지 않는다.

보고와 중단 기준

  1. 각 마일스톤 종료 시 변경 파일, 실제 실행 명령, 확인 가능한 결과, 남은 차단 이슈만 간단히 보고한다.
  2. 엔진의 상태 연속성이나 활성 셀 계산이 지원되지 않으면 최소 수정 지점을 조사한 뒤 멈추고 사용자 판단을 받는다.
  3. 핵심 물리 모델, 입력 데이터의 의미, 지도 기술, 시스템 구조를 바꾸어야 하는 경우 먼저 승인받는다.
  4. 문제가 해결되지 않았는데 반복적인 시도와 검증으로 시간을 소비하지 않는다. 막힌 이유와 대안을 구체적으로 제시한다.
  5. “작동한다”는 주장은 실행 결과와 연결되어야 한다. 코드가 존재한다는 이유만으로 완료 처리하지 않는다.
