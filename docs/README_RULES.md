# README 작성 및 유지 규칙

이 규칙은 모든 README.md 수정 작업에 적용한다. AGENTS.md에서 이 문서를 참조하도록 한다.

## 고정 구조

README.md의 제목은 `# AntiFlood`로 유지한다. 다음 다섯 개의 2단계 제목을 순서대로 사용한다. 사용자 승인 없이 섹션을 추가, 삭제, 개명하거나 순서를 변경하지 않는다.

1. 프로젝트 주제
2. 프로젝트 동기
3. 빅데이터 알고리즘의 적용
4. 시스템 아키텍처
5. 리파지토리 구조

프로젝트 주제에는 다음 문장만 사용하며, 단어와 문장부호를 포함해 수정하지 않는다.

> 대규모 시공간 강우 데이터가 지속적으로 유입되는 상황에서, 입력에 의해 변화하는 서울 전역의 침수 상태를 제한된 계산 자원으로 얼마나 빠르게 갱신 가능한가?

## 작성 원칙

- 프로젝트 동기는 문제의 특성, 기존 방식의 한계, AntiFlood의 접근 방식 순으로 설명한다.
- 빅데이터 알고리즘의 적용은 기법과 실제 적용 방식을 연결하고, 줄어드는 계산 또는 저장 비용과 정보 손실을 설명한다. 강의에서 배운 알고리즘과 일반적인 구현 기법을 구분한다.
- 시스템 아키텍처는 `docs/assets/architecture.png`의 이미지와 짧은 설명을 사용한다. Mermaid, ASCII 아키텍처 도식 또는 기술 스택 목록으로 대체하지 않는다. 구조가 바뀌면 실제 코드를 확인하고 이미지를 갱신한다.
- 리파지토리 구조는 실제 디렉터리와 주요 파일만 간결하게 표시한다.
- 한국어 문장에는 엠대시와 가운데 점을 사용하지 않는다. 나열은 쉼표나 접속사로 처리한다. 한 문장에는 하나의 핵심 내용을 담는다.
- 추상적인 표현과 기능을 단순히 나열하는 문장을 피한다. 어떤 대상에 무엇을 하는지, 왜 필요한지를 명확히 쓴다.
- 100m Tile은 작업 관리 단위이며 30m 격자는 물리 계산 단위다. 단일 머신의 OpenMP 병렬 처리를 분산 처리로 설명하지 않는다.
- 과거 강우 재생을 실시간 관측 API 연동으로 표현하지 않는다. 배수 가정값과 실제 관측값을 구분한다. 서울 전역을 목표로 한다는 사실과 실제 계산한 지역 범위를 구분한다.
- 측정하지 않은 성능 향상이나 정확도를 확정적으로 주장하지 않는다. 아직 구현되지 않은 기능은 구현된 것처럼 설명하지 않는다.
- 설치, 실행, 데이터 출처, 구현 세부사항은 관련 문서에 두고 README 하단에서 링크한다.
- 코드 변경과 관련 없는 README 전체 재작성은 하지 않는다. 필요한 내용만 갱신하고 기존 구조와 문체를 보존한다.
