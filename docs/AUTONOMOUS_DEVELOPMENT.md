# AntiFlood 프로젝트 개발 및 자율 실행 지침

## 1. 작업의 목적

앞서 제공한 「AntiFlood 프로젝트 개선 방향」을 이번 개발 작업의 최상위 명세로 사용한다.

이번 작업의 목적은 기존 AntiFlood를 새로운 설계 방향에 맞게 개선하고, 실제로 실행하고 발표할 수 있는 완성된 프로젝트로 만드는 것이다.

새로운 기술을 최대한 많이 적용하거나, 코드의 추상화 수준을 높이거나, 많은 테스트를 통과시키는 것이 목적이 아니다.

**사용자가 정의한 프로젝트를 가장 단순하고 신뢰할 수 있는 형태로 완성하는 것이 목적이다.**

구현, 시스템 아키텍처, API, 대시보드, README 및 관련 문서는 모두 동일한 프로젝트 의도를 반영해야 한다.

사용자는 제품의 방향과 요구사항을 결정한다. 개발 에이전트는 그 방향을 실현하기 위한 세부 구현을 자율적으로 결정한다.

자율성은 구현 방법을 결정할 수 있는 권한이지, 프로젝트의 방향이나 목표를 변경할 수 있는 권한이 아니다.

## 2. 지침의 우선순위

작업 중 여러 지침이 충돌하는 경우 다음 순서로 판단한다.

1. 사용자가 명시적으로 전달한 최신 요구사항
2. 「AntiFlood 프로젝트 개선 방향」
3. 본 개발 및 자율 실행 지침
4. `.ralph/GOAL.md`의 완료 조건
5. `AGENTS.md`와 `docs/DEVELOPMENT_PRINCIPLES.md`
6. 각 작업에 적용되는 SKILL 및 기타 개발 지침
7. 기존 구현에서 사용한 관례

기존 지침이 새로운 개선 방향과 충돌한다면, 기존 지침을 기계적으로 따르지 말고 충돌하는 부분을 정리한다.

다만 변경 권한이 제한된 파일은 자율 개발 라운드에서 임의로 수정하지 않는다. 필요한 변경은 개발 루프 시작 전 초기 설정 단계에서 처리한다.

SKILL은 작업의 품질과 효율을 높이기 위한 도구다. SKILL에 특정 작업 방식이 제시되어 있다는 이유만으로 불필요한 테스트, 문서, 기능, 추상화 계층을 추가하지 않는다.

프로젝트에 필요한 부분만 선택적으로 적용한다.

## 3. 변경할 수 없는 프로젝트의 핵심 요구사항

### 3.1. 연구 질문

프로젝트의 연구 질문은 다음 문장으로 고정한다.

대규모 시공간 강우 데이터가 지속적으로 유입되는 상황에서, 입력에 의해 변화하는 서울 전역의 침수 상태를 제한된 계산 자원으로 얼마나 빠르게 갱신 가능한가?

사용자 승인 없이 연구 질문의 표현, 범위 또는 연구 목적을 변경하지 않는다.

AntiFlood는 빅데이터개론 과목의 프로젝트다. 고정밀 도시 수문학 모델, 상업용 재난 대응 시스템 또는 범용 시뮬레이션 플랫폼을 만드는 것이 목적이 아니다.

### 3.2. 물리 계산 원칙

- 서울 전역의 모든 유효 격자를 계산 대상으로 유지한다.
- 기존 30m 공간 해상도를 유지한다.
- 강우량이 적거나 침수 위험도가 낮다는 이유로 특정 지역의 수평 유동 계산을 임의로 생략하지 않는다.
- 강우, 배수, 물의 유입 및 유출을 시간에 따라 반영한다.
- 강우가 종료된 이후에도 기존 물의 이동과 배수를 계산한다.
- 질량 보존, 비음수 수심 및 수치적 안정성을 유지한다.
- 공통 결과 저장 시각에는 모든 격자의 상태가 동일한 물리 시각까지 계산되어 있어야 한다.

지역별 계산 주기를 조절하는 것은 허용하지만, 특정 지역을 사실상 계산 대상에서 제외하는 방식으로 기존 알고리즘을 재현해서는 안 된다.

### 3.3. 유지해야 하는 구성 요소

다음 요소는 특별한 문제가 없는 한 유지한다.

- 기존 데이터셋 및 데이터 전처리 구조
- 서울시 DEM
- 30m 물리 계산 격자
- 100m Tile을 기반으로 한 공간 관리 구조
- WCA2D 물리 계산 모델
- C++ 및 OpenMP 병렬 처리 환경
- Python 기반 데이터 처리 구조
- FastAPI
- MapLibre 기반 대시보드
- 기존 실행 및 결과 조회 기능
- Reference와 개선 방식의 비교 구조

기존 시스템으로 해결할 수 있는 문제를 해결하기 위해 다른 프레임워크나 기술 스택을 도입하지 않는다.

## 4. 구현 범위

### 4.1. 필수 개발 작업

이번 작업에서 수행해야 하는 핵심 작업은 다음과 같다.

1. 위험도 기반 선택적 수평 유동 계산 정책 제거
2. 서울 전역의 지속적인 물리 계산 구조 확보
3. 강우 입력의 순차 처리 및 처리 완료 후 폐기
4. Decaying Window를 활용한 강우 이력 요약
5. 지역별 Adaptive Time Stepping의 구현 가능성 검토 및 구현
6. 서로 다른 계산 주기 사이의 물 이동 처리
7. 기존 OpenMP 병렬 처리 구조 활용 및 스레드 설정 개선
8. 새로운 알고리즘에 맞게 API 및 대시보드 수정
9. 기존 Reference 대비 성능과 정확성 비교
10. README, 시스템 아키텍처 및 관련 문서 갱신

### 4.2. 기존 구현에서 재사용할 개념

다음 개념은 기존 코드에 이미 적용되어 있으므로 불필요하게 다시 구현하지 않는다.

| 개념 | 기존 적용 위치 |
|---|---|
| Pregel과 유사한 BSP 모델 | WCA2D의 동기적 반복 계산 구조 |
| Parallel Processing | OpenMP 병렬 처리 |
| Sparse Representation | 격자별 인접 연결 정보 |
| Temporal Sampling | 10분 단위 전체 수심 지도 저장 |
| Decaying Window | 강우 이력 요약 |
| Data Stream Processing | 강우 데이터 순차 재생 |

기존 코드와 강의 개념의 대응 관계를 명확하게 정리하되, 단순히 기존 코드에 새로운 알고리즘의 이름을 붙이는 방식으로 개발하지 않는다.

### 4.3. 작업 범위에 포함하지 않는 사항

다음 작업은 사용자가 별도로 요청하지 않는 한 진행하지 않는다.

- 새로운 물리 계산 엔진 개발
- WCA2D를 다른 수문학 모델로 교체
- 실제 Pregel, Hadoop, Spark 등의 분산 처리 프레임워크 도입
- Kafka, Redis, Kubernetes 등 새로운 인프라 구축
- 새로운 데이터베이스 도입
- 실시간 기상 관측 API 연동
- 새로운 데이터셋의 대규모 탐색 및 수집
- 머신러닝 기반 침수 예측
- LLM을 활용한 자동 침수 대응 또는 의사결정
- 새로운 사용자 인증 및 계정 관리 기능
- 클라우드 배포
- 범용 시뮬레이션 플랫폼화
- 동적 부하 분산 시스템
- 복잡한 자동 튜닝 시스템
- 프로젝트와 직접 관련되지 않는 기능 개선

기존 선택 기능은 핵심 개발을 방해하지 않는 한 유지한다. 이번 작업을 이유로 해당 기능을 확장하거나 별도의 개선 작업을 진행하지 않는다.

## 5. 핵심 알고리즘 구현 지침

### 5.1. Data Stream Processing

강우 데이터를 시간순으로 읽고 처리한다.

현재 강우 구간을 계산하는 데 필요한 입력만 실행 중인 스트림 처리기에 유지한다. 해당 구간의 처리가 완료되면 이전 입력에 대한 참조를 제거한다.

전체 강우 이력을 메모리에 적재하거나, 처리한 입력을 별도의 배열에 계속 누적하지 않는다.

현재 데이터 로더와 Replay 구조가 실제로 전체 강우 구간을 미리 적재하고 있는지 확인한다. 단순히 반복문으로 데이터를 순차 처리한다는 이유만으로 제한된 메모리의 스트리밍 처리가 구현되었다고 판단하지 않는다.

원본 강우 데이터셋은 실험 재현을 위해 보존한다.

처리된 입력을 메모리에서 폐기하는 것과 결과 기록에 관측 강우량을 저장하는 것은 별개의 문제다. 기존 결과 조회 기능에 필요한 정보는 목적을 확인한 후 유지한다.

### 5.2. Decaying Window

기존 감쇠 가중합 구조를 재사용한다.

초기 감쇠 계수는 기존 구현의 0.8을 사용하되, 이를 최적의 값이라고 주장하지 않는다.

Decaying Window는 최근 강우의 영향을 제한된 크기의 상태로 요약하고 지역별 계산 주기를 결정하는 보조 지표로 사용한다.

감쇠 강우량이 감소한다고 해서 실제 격자의 물을 제거하지 않는다.

Sliding Window는 정확한 최근 누적 강우량을 필요로 하는 기능이 있는지 확인한다. 명확한 용도가 없다면 제거하고, 필요한 기존 기능이 있다면 그 용도에 한정하여 유지한다.

강의에서 배웠다는 이유만으로 사용 목적이 없는 알고리즘을 유지하지 않는다.

### 5.3. Adaptive Time Stepping

이번 프로젝트의 핵심 신규 개발 대상이다.

상태 변화가 빠른 지역은 짧은 계산 간격을 사용하고, 상태 변화가 완만한 지역은 상대적으로 긴 계산 간격을 사용한다.

기존 Tile을 지역별 계산 주기를 관리하는 단위로 활용하는 방식을 우선 검토한다.

계산 주기를 결정할 때 다음 정보를 활용할 수 있다.

- 현재 강우량
- 감쇠 강우량
- 현재 수심
- 수심 변화율
- 인접 지역에서 전달되는 유량
- 물리 모델의 수치 안정성 조건

위 항목을 반드시 모두 구현해야 하는 것은 아니다. 필요한 최소한의 판단 기준으로 정확성과 안정성을 확보할 수 있다면 단순한 방식을 선택한다.

계산 주기는 소수의 이산적인 단계로 제한한다. 격자마다 서로 다른 임의의 실수 시간 간격을 관리하는 복잡한 스케줄러를 개발하지 않는다.

기존 WCA2D의 시간 간격 제한과 유량 계산 방식부터 확인한다.

Reference가 이미 15초 이하의 가변 시간 간격을 사용한다는 점을 고려해야 한다. 단순히 일부 지역의 계산 주기를 더 짧게 설정하는 것은 계산량 절감이 아니다.

개선 방식은 실제 물리 연산 횟수를 줄일 수 있는 구조여야 한다.

강우량은 계산 주기를 단축하는 보조 조건으로 활용하고, 시간 간격의 최종 제한은 물리적 안정성에 따라 결정한다.

### 5.4. 경계 유량 처리

서로 다른 계산 주기를 사용하는 지역 사이에서도 물의 이동은 유지되어야 한다.

경계를 통과하는 물의 부피를 누락하거나 중복 반영하지 않는다.

출발 격자에서 차감한 물의 부피와 도착 격자에 반영한 물의 부피가 일치해야 한다.

서로 다른 물리 시각의 상태를 참조하는 문제를 고려하고, 필요한 시점에 지역 간 상태를 동기화한다.

질량 보존이 성립한다는 사실만으로 시간 적분의 정확성과 수치 안정성이 보장된다고 판단하지 않는다.

기존 유출 커널의 계산 특성과 호환되는 가장 단순한 방법을 선택한다.

### 5.5. Threshold 선정

임계값은 다음 순서로 결정한다.

1. 물리 모델의 수치 안정성 조건 확인
2. 의미 있는 소수의 후보 설정
3. 동일 조건의 Reference와 비교
4. 허용 가능한 오차와 계산량을 고려하여 선정

수십 또는 수백 개의 매개변수 조합을 탐색하는 자동 튜닝 체계를 구축하지 않는다.

초기에는 대표적인 후보 2~3개로 충분한지 확인한다. 추가 후보가 필요한 경우에도 어떤 설계 판단을 해결하기 위한 것인지 명확히 한다.

임계값을 선정한 사례와 최종 평가 사례를 가능한 한 구분한다.

허용 가능한 오차의 기준이 사용자에게 확정되지 않았다면, 임의의 수치를 합격 기준으로 확정하지 않는다. 실제 측정된 오차와 성능을 제시하여 판단할 수 있도록 한다.

특정 성능 수치를 달성하기 위해 물리적 조건이나 정확성 평가 기준을 변경하지 않는다.

### 5.6. 구현 실패 시 대응

Adaptive Time Stepping이 기존 WCA2D 구조에서 안전하게 구현되기 어렵다면, 다음과 같이 대응한다.

- 해결 가능한 국소적인 구현 문제는 직접 수정한다.
- 기존 엔진 전체를 교체해야 하는 문제인지 구분한다.
- 해결책의 복잡성이 얻을 수 있는 이점보다 큰지 판단한다.
- 작동하는 Reference 구현을 보존한다.
- 근본적인 문제가 해결되지 않으면 BLOCKED 상태로 보고한다.

구현하기 어렵다는 이유로 기존 선택적 영역 계산을 다시 도입하거나, 전혀 다른 알고리즘으로 연구 방향을 변경하지 않는다.

## 6. 오버엔지니어링 방지

### 6.1. 변경의 필요성 판단

코드를 수정하기 전에 다음 질문에 답한다.

- 이번 변경은 어떤 사용자 요구사항을 충족하는가?
- 기존 코드로 해결할 수 없는 이유가 무엇인가?
- 더 간단한 구현 방법은 없는가?
- 변경하지 않을 경우 실제로 어떤 문제가 발생하는가?

명확하게 답할 수 없는 변경은 진행하지 않는다.

작업 항목은 개선 명세 또는 필수 완료 조건과 연결되어 있어야 한다.

### 6.2. 코드 구조 원칙

기존 파일에 합리적으로 추가할 수 있는 기능은 기존 파일을 활용한다.

다음과 같은 구현을 피한다.

- 한 번만 사용되는 기능을 위한 범용 인터페이스
- 실제 사용 계획이 없는 플러그인 구조
- 불필요한 Factory, Manager, Registry, Adapter
- 하나의 간단한 연산을 위한 과도한 클래스 분리
- 중복된 설정 계층
- 미래의 확장 가능성을 위한 코드
- 기존 기능과 사실상 동일한 새로운 모듈
- 의미 없는 Wrapper 함수
- 단순한 배열 연산을 위한 새로운 데이터 처리 프레임워크

파일을 추가해야 할 때는 기존 구조로 해결하기 어려운 이유가 있어야 한다.

반대로 새로운 모듈로 분리하는 것이 명확하게 복잡성을 줄인다면 합리적인 파일 추가는 허용한다.

파일 수나 코드 줄 수에 기계적인 제한을 적용하지 않는다.

### 6.3. 의존성 관리

새로운 외부 라이브러리를 도입하기 전에 Python 표준 라이브러리, 기존 의존성 및 C++ 코드로 해결할 수 있는지 확인한다.

새로운 의존성으로 인해 설치 및 실행 과정이 복잡해지지 않도록 한다.

특히 기존 WSL 환경과 Windows 실행 방식을 훼손하지 않는다.

### 6.4. 리팩터링 범위

이번 작업과 직접 관련된 코드만 리팩터링한다.

정상적으로 작동하는 코드를 선호하는 스타일과 다르다는 이유로 재작성하지 않는다.

전체 리파지토리의 코드 스타일 변경, 일괄적인 파일명 변경, 대규모 디렉터리 재구성을 진행하지 않는다.

기존 설계와 충돌하는 코드는 실제 의존성을 확인한 후 제거한다. 과거 구현과 새로운 구현을 목적 없이 동시에 유지하지 않는다.

Reference와 새로운 개선 방식의 비교에 필요한 코드는 유지한다.

## 7. 테스트 및 실험 통제

### 7.1. 검증의 목적

테스트는 구현 결과가 올바르게 작동하는지 확인하는 수단이다.

테스트를 작성하거나 실행하는 것 자체가 프로젝트의 발전을 의미하지 않는다.

**구현의 완료 여부 또는 중요한 설계 판단에 영향을 주는 테스트만 수행한다.**

새로운 테스트를 시작하기 전에 다음을 확인한다.

- 확인하려는 가설 또는 요구사항은 무엇인가?
- 기존 검증 결과로 충분하지 않은 이유는 무엇인가?
- 결과가 달라지면 실제 구현에 어떤 영향을 주는가?
- 더 저렴하고 간단한 검증 방법은 없는가?

답할 수 없다면 해당 테스트를 수행하지 않는다.

### 7.2. 필수 검증 범위

| 검증 대상 | 확인할 내용 |
|---|---|
| 기본 실행 | 기존 실행 방식으로 서버와 대시보드가 정상적으로 실행되는가 |
| 물리 정확성 | 질량 보존, 비음수 수심, 유한한 계산 결과가 유지되는가 |
| 경계 유량 | 서로 다른 계산 주기를 가진 지역 사이에서 물이 누락되거나 중복되지 않는가 |
| 시간 동기화 | 모든 격자가 동일한 결과 시각까지 계산되는가 |
| 스트리밍 처리 | 강우 입력이 순서대로 처리되고 불필요한 이력이 누적되지 않는가 |
| 계산 성능 | Reference 대비 물리 연산 횟수와 처리 시간이 어떻게 달라지는가 |
| 결과 정확성 | Reference 대비 RMSE와 IoU가 어떻게 달라지는가 |
| 대시보드 | 핵심 실행, 결과 조회, 지도 비교 기능이 실제로 작동하는가 |

새로운 알고리즘의 핵심 안전 조건을 확인하는 테스트는 생략하지 않는다.

다만 위 항목을 충족하기 위해 여러 개의 유사한 테스트 체계를 별도로 구축할 필요는 없다.

### 7.3. 검증 진행 순서

**1단계: 작은 입력으로 핵심 구현 확인**

작은 격자 또는 짧은 강우 구간으로 물리적 불변조건과 새로운 계산 주기의 동작을 확인한다.

**2단계: 실제 데이터로 기능 확인**

기존에 준비된 지역별 강우 데이터를 사용하여 시스템이 실제 데이터에서도 작동하는지 확인한다.

**3단계: 최종 성능 측정**

핵심 구현이 안정적으로 작동한 이후 서울 전역에 대해 Reference와 개선 방식을 비교한다.

매 코드 수정 직후 서울 전역의 전체 시뮬레이션을 실행하지 않는다.

### 7.4. 테스트 예산

다음 수치는 초기 검증 범위를 통제하기 위한 작업 예산이다.

- 핵심 물리 검증은 소수의 대표 입력으로 구성한다.
- 임계값 비교는 초기 후보 2~3개를 기본으로 한다.
- CPU 스레드 비교는 기존 4스레드와 사용 가능한 추가 설정 1~2개를 기본으로 한다.
- 서울 전역의 성능 비교는 구현이 확정된 이후 수행한다.
- 전체 성능 비교는 가능한 경우 각 최종 조건에서 3회 측정하고 중앙값과 변동 범위를 기록한다.

위 예산은 검증을 기계적으로 제한하는 절대적인 테스트 개수는 아니다.

물리적 정확성을 훼손하는 문제가 발견되었거나 측정 결과가 불안정한 경우에는 해당 문제를 해결하기 위한 추가 검증을 허용한다.

다만 추가 검증이 필요한 이유와 결과에 따른 후속 조치를 명확하게 기록한다.

환경 문제로 동일한 검증이 반복해서 실패하면 무한히 재시도하지 않는다. 원인을 확인하고 해결할 수 없는 경우 BLOCKED로 처리한다.

### 7.5. 금지하는 테스트 행동

다음 행동을 하지 않는다.

- 이미 확인한 사실을 다른 이름의 테스트로 계속 재확인
- 코드 변경 없이 동일한 벤치마크 반복
- 검증 프로그램을 검증하기 위한 새로운 검증 프로그램 작성
- 테스트 커버리지 수치를 높이기 위한 테스트 추가
- 실제 사용자 경로와 관련 없는 모든 예외 상황의 전수 검사
- 테스트 결과를 저장하기 위한 새로운 데이터 관리 시스템 구축
- 전체 임계값 및 매개변수 조합 탐색
- 미세한 성능 차이를 설명하기 위한 불필요한 실험 확대
- 측정 결과를 정당화하기 위한 장황한 보고서 작성
- 테스트 프레임워크 도입 자체를 개선 작업으로 선정

이미 검증한 코드가 변경되지 않았다면 기존 검증 근거를 재사용한다.

### 7.6. 성능 측정의 정직성

Reference와 개선 방식의 성능은 동일한 CPU 자원과 동일한 입력 조건에서 먼저 비교한다.

알고리즘으로 인한 성능 향상과 CPU 스레드 증가로 인한 성능 향상을 구분한다.

다음 항목을 혼동하지 않는다.

- 총 물리 연산 횟수
- 실제 실행 시간
- CPU 시간
- 메모리 사용량
- 저장 및 시각화 시간

결과가 기대보다 나쁘더라도 수치를 숨기거나 평가 기준을 변경하지 않는다.

수심 RMSE와 침수 영역 IoU는 기존 Reference와의 일치도를 나타낸다. 실제 침수 예측 정확도라고 설명하지 않는다.

## 8. 대시보드 품질 관리

### 8.1. 대시보드의 목적

대시보드는 AntiFlood의 핵심 사용자 인터페이스이며 발표 시 프로젝트의 연구 결과를 보여주는 수단이다.

사용자는 코드를 읽지 않아도 다음을 이해할 수 있어야 한다.

1. 현재 어떤 강우 데이터를 처리하고 있는가?
2. 서울의 어느 지역에 물이 쌓이고 있는가?
3. 지역마다 계산 주기가 어떻게 다른가?
4. Reference와 개선 방식 사이에 어떤 차이가 있는가?
5. 얼마만큼의 계산량과 시간이 절약되었는가?
6. 계산량 절약으로 어떤 오차가 발생했는가?

이 목적에 직접 기여하지 않는 시각적 요소는 추가하지 않는다.

### 8.2. 기존 디자인 시스템 유지

기존 `web/index.html`, `web/style.css`, `web/app.js`의 구성과 디자인을 먼저 이해한다.

현재 디자인은 다시잇다 프로젝트의 스타일 기준을 활용하고 있다.

다음 요소를 유지한다.

- S-Core Dream 글꼴
- 연한 청색 배경
- 흰색 패널
- 파란색 주요 조작 버튼
- 기존 타이포그래피 및 색상 체계
- 일관된 패널과 버튼의 모서리 처리
- 주요 실행 버튼의 56px 높이
- 보조 조작 요소의 44px 이상 높이
- 지도 중심의 화면 구성

기존 CSS 변수와 컴포넌트 스타일을 우선 재사용한다.

새로운 디자인 시스템, CSS 프레임워크 또는 프론트엔드 프레임워크를 도입하지 않는다.

기존 화면의 시각적 정체성을 변경하지 않는다.

### 8.3. 화면 구성

현재 화면의 세 가지 주요 영역을 유지한다.

**중앙 지도 영역**

Reference와 개선 방식의 침수 상태를 같은 시각과 동일한 공간 범위에서 비교한다.

지도는 화면에서 가장 큰 시각적 비중을 가져야 한다.

**하단 시간 및 분석 영역**

시간 막대, 주요 성능 지표, 강우 및 수심 변화 등을 표시한다.

지도와 시간 막대가 서로 연동되어야 한다.

**우측 실행 설정 영역**

시나리오, 계산 지역, 배수 조건, CPU 스레드 및 실행 제어 기능을 배치한다.

중요도가 낮은 설정은 기존 접이식 영역에 배치한다.

### 8.4. 새 알고리즘에 필요한 시각화

기존 활성 Tile 시각화는 새로운 지역별 계산 주기 시각화로 변경한다.

필요한 결과 레이어는 다음과 같다.

- 모의 수심
- 지역별 계산 주기
- Reference 대비 수심 차이

기존 침수흔적도, 배수능력, 관측소 강우 등 정상적으로 작동하는 입력 및 비교 레이어는 유지한다.

계산 주기 시각화는 실제 실행 중 사용한 계산 주기 또는 측정된 지역별 계산 빈도를 기반으로 한다.

실제 알고리즘과 무관한 임의의 위험도나 가상의 계산 주기를 표시하지 않는다.

한 저장 구간 안에서 계산 주기가 달라진 경우에는 화면에 표시하는 값이 마지막 계산 주기인지, 평균 주기인지 명확하게 표현한다.

### 8.5. 지도 비교의 일관성

Reference와 개선 방식의 지도에는 다음 기준을 동일하게 적용한다.

- 지도 위치
- 확대 수준
- 지도 방향
- 3D 지형 시점
- 표시하는 물리 시각
- 수심 색상 범례
- 공간 해상도
- 계산 범위

두 지도에서 동일한 수심이 서로 다른 색상으로 나타나서는 안 된다.

계산이 완료되지 않은 시각의 결과를 기존 결과나 가상 데이터로 채워 표시하지 않는다.

결과가 없는 상태와 수심이 0인 상태를 구분한다.

### 8.6. 핵심 성능 지표

다음 정보를 우선적으로 표시한다.

| 지표 | 표시 목적 |
|---|---|
| 최대 모의 수심 | 현재 물리 상태 이해 |
| 현재 강우량 | 입력 조건 이해 |
| 계산 시간 | 처리 성능 확인 |
| Speedup | Reference 대비 실행 속도 비교 |
| 물리 계산량 감소율 | 알고리즘의 효과 확인 |
| 수심 RMSE | 수심 차이 확인 |
| 침수 영역 IoU | 침수 영역의 일치도 확인 |

기존 활성 격자 수 및 활성 Tile 수처럼 새 알고리즘의 의미와 일치하지 않는 지표는 제거하거나 적절한 지표로 변경한다.

지표를 추가하는 것보다 현재 지표가 무엇을 의미하는지 명확하게 표현하는 것이 중요하다.

측정되지 않은 값은 0 또는 가상의 숫자로 표시하지 않는다.

### 8.7. AI가 생성한 전형적인 저품질 UI 금지

다음 디자인을 추가하지 않는다.

- 목적 없는 카드의 반복
- 불필요하게 큰 제목
- 과도한 배지 및 상태 표시기
- 기능과 무관한 장식용 아이콘
- 그라데이션을 남용한 배경
- 과도한 그림자 및 글래스모피즘
- 의미 없는 애니메이션
- 실제 데이터와 무관한 그래프
- 여러 가지 색상을 무분별하게 사용하는 범례
- 모든 정보를 동일한 중요도로 나열하는 레이아웃
- 동일한 내용을 반복하는 패널
- 설명만 길고 실제 조작은 어려운 화면

대시보드는 발표용 장식물이 아니라 실제 데이터를 탐색하고 비교할 수 있는 도구여야 한다.

### 8.8. 기존 사용자 흐름 보존

다음 사용자 흐름이 정상적으로 작동해야 한다.

기존 위험도 기반 선택적 수평 유동 계산이 제거되었다면, 프로젝트 동기에서도 해당 방식을 제거한다.

일반적인 재난 문제의 심각성이나 사회적 기대효과를 장황하게 설명하지 않는다.

### 9.4. 빅데이터 알고리즘의 적용

알고리즘의 이름을 나열하는 것에서 그치지 않는다.

각 알고리즘에 대해 다음 내용을 전달한다.

- 시스템의 어느 부분에 사용되는가?
- 실제로 어떤 정보를 처리하는가?
- 어떤 자원 사용량을 줄이는가?
- 어떤 정보를 포기하는가?
- 강의에서 배운 방법을 직접 적용한 것인가, 원리를 응용한 것인가?

최종적으로 실제 구현된 개념만 설명한다.

예를 들어 Pregel 프레임워크를 사용하지 않았다면 Pregel을 도입했다고 설명하지 않는다. 기존 엔진이 Pregel의 BSP 모델과 유사한 동기적 반복 계산 구조를 사용한다고 설명한다.

Temporal Sampling이 강의의 해시 기반 샘플링과 동일한 알고리즘인 것처럼 표현하지 않는다.

Adaptive Time Stepping이 강의에 직접 등장한 알고리즘인 것처럼 설명하지 않는다.

이 섹션에는 실제 측정된 성능 및 정확성 결과를 간결한 표로 포함할 수 있다.

## 11. Ralph 자율 개발 루프 초기 설정

현재 Ralph Loop의 완료 조건은 기존 선택적 영역 계산 방식을 기준으로 작성되어 있다.

새로운 개발을 시작하기 전에 기존 지침과 목표를 새로운 개선 명세에 맞게 정리해야 한다.

### 11.1. 초기 설정 단계

자율 개발 라운드를 시작하기 전에 다음 작업을 한 번 수행한다.

1. `git status`를 확인하고 사용자의 기존 변경사항을 보존한다.
2. 현재 코드와 관련 개발 지침을 확인한다.
3. 새로운 개선 명세를 저장소에서 참조 가능한 형태로 보관한다.
4. `AGENTS.md`가 새로운 개선 명세와 실행 지침을 참조하도록 정리한다.
5. 기존 개발 원칙에서 선택적 영역 계산을 프로젝트의 고정 목적으로 규정한 부분을 수정한다.
6. `.ralph/GOAL.md`를 새로운 완료 조건으로 갱신한다.
7. `.ralph/PROMPT.md`가 새로운 목표와 작업 범위를 참조하도록 수정한다.
8. `scripts/ralph-verify.py`의 기존 완료 조건이 새로운 요구사항과 일치하도록 필요한 부분을 수정한다.
9. 기존 DONE 상태가 새로운 작업을 조기에 종료시키지 않도록 새로운 작업 상태를 초기화한다.
10. 기존 실행 기록과 Git 이력을 보존한다.

기존 Ralph 컨트롤러는 GOAL, PROMPT, 검증 스크립트 및 AGENTS 등의 변경을 실행 중에 제한한다.

따라서 보호 파일 변경은 자율 개발 라운드 내부에서 시도하지 않는다.

위 초기 설정에 필요한 수정은 루프를 시작하기 전 별도의 준비 작업으로 수행한다.

기존 컨트롤러가 요구하는 깨끗한 작업 트리와 체크포인트 조건을 충족해야 한다. 사용자 변경사항을 삭제하거나 무단으로 커밋 및 푸시하여 이를 충족하지 않는다.

### 11.2. 컨트롤러 수정 제한

기존 `scripts/ralph-loop.py`를 최대한 유지한다.

새로운 기능을 구현하기 위해 별도의 에이전트 오케스트레이션 프레임워크를 개발하지 않는다.

현재 컨트롤러의 라운드 제한, 시간 제한, 재시도 제한, 보호 파일 관리 및 독립 검증 구조를 우선 활용한다.

현재 기본 설정은 최대 6라운드, 라운드당 900초, 전체 5,400초, 최대 2회 시도다.

이 제한은 개발 에이전트가 임의로 확대하거나 제거할 수 없다.

시간 또는 라운드 제한에 도달하면 미완료 상태와 실제 진행 상황을 기록한다.

사용자가 설정한 실행 범위를 넘어 자동으로 새로운 실행을 시작하지 않는다.

## 12. 자율 개발 루프 실행 방식

### 12.1. 작업 상태 관리

완료 조건을 고정하고 각 항목에 다음 상태 중 하나를 부여한다.

| 상태 | 의미 |
|---|---|
| PENDING | 작업이 필요함 |
| IN_PROGRESS | 현재 구현 중 |
| VERIFIED | 구현 및 필요한 확인 완료 |
| BLOCKED | 근본적인 문제로 사용자 판단 또는 외부 조건이 필요함 |

기존에 구현된 기능을 찾기 전에 미구현이라고 판단하지 않는다.

완료된 요구사항은 관련 코드가 변경되지 않는 한 다시 검증하거나 재구현하지 않는다.

라운드가 바뀔 때마다 전체 프로젝트를 처음부터 분석하지 않는다. 기존 STATE와 HISTORY를 활용하고 현재 작업에 필요한 코드만 확인한다.

### 12.2. 반복 실행 과정

각 라운드는 다음 과정을 수행한다.

**ANALYZE**

현재 상태와 고정된 완료 조건의 차이를 확인한다.

**SELECT**

가장 중요한 미충족 요구사항을 선택한다.

기존 코드의 실제 결함이나 미완성 구현을 기준으로 작업을 선택한다.

**IMPLEMENT**

선택한 요구사항을 해결하기 위한 최소한의 변경을 수행한다.

분석만 반복하거나 구현 계획만 작성하고 종료하지 않는다.

**VERIFY**

변경한 내용에 필요한 검증을 수행한다.

컨트롤러가 최종 독립 검증을 수행하도록 되어 있다면 해당 검증을 각 라운드에서 반복하지 않는다.

**RECORD**

실제로 변경한 내용, 검증 결과 및 남은 작업을 간결하게 기록한다.

**CONTINUE OR STOP**

남은 필수 요구사항이 있다면 다음 라운드로 진행한다.

완료 조건을 충족했다면 종료한다.

### 12.3. 작업 우선순위

작업은 다음 순서로 진행한다.

| 우선순위 | 대상 |
|---|---|
| 1 | 핵심 물리 계산 구현 |
| 2 | 강우 스트리밍 및 적응형 계산 주기 |
| 3 | 정확성 및 안정성 확보 |
| 4 | 실제 계산 성능 개선 |
| 5 | API와 대시보드 연결 및 수정 |
| 6 | README와 아키텍처 이미지 갱신 |
| 7 | 불필요한 기존 코드 및 설정 정리 |
| 8 | 최종 실행 및 완료 조건 확인 |

문서 작성이나 벤치마크 결과 정리가 핵심 구현보다 앞서서 진행되지 않도록 한다.

다만 구현에 반드시 필요한 설계 판단이나 검증은 선행할 수 있다.

### 12.4. 유효하지 않은 작업

다음 작업만을 이유로 새로운 개발 라운드를 시작하지 않는다.

- 문장 표현을 더 세련되게 변경
- 코드 스타일 정리
- 새로운 개선 가능성 탐색
- 추가 기술 스택 조사
- 이미 정상 작동하는 기능의 재검증
- 더 많은 테스트 작성
- 사용되지 않는 기능의 고도화
- 사소한 성능 최적화 가능성 조사
- 문서의 분량 확대

미충족 요구사항이 없다면 새로운 작업을 만들어 내지 않는다.

## 13. 에이전트의 의사결정 권한

### 자율적으로 결정할 수 있는 사항

- 기존 함수를 재사용하는 방법
- 필요한 배열 및 자료구조 선택
- 지역별 계산 주기 관리의 구체적인 구현
- 기존 API의 합리적인 수정
- 필요한 범위의 UI 컴포넌트 변경
- 기본적인 오류 처리
- 관련 코드의 국소적인 리팩터링
- 임시 성능 측정 방법
- 문서와 코드 사이의 불일치 수정

### 사용자 승인 없이 결정할 수 없는 사항

- 연구 질문 변경
- 공간 해상도 변경
- 물리 계산 모델 교체
- 전체 시스템 아키텍처의 대규모 재구성
- 새로운 핵심 기능 추가
- 확정되지 않은 정확성 허용 기준의 최종 결정
- 프로젝트의 주요 디자인 변경
- 새로운 외부 서비스 및 유료 서비스 도입
- 기존 데이터셋 또는 사용자 결과 삭제
- 새로운 근사 기법으로의 연구 방향 변경
- 자율 실행 시간 및 라운드 제한 확대

사소한 구현 선택을 반복적으로 사용자에게 질문하지 않는다.

반대로 사용자에게 위임받지 않은 중요한 결정은 진행을 위해 임의로 확정하지 않는다.

## 14. 최종 완료 조건

다음 완료 조건을 새로운 자율 개발 루프의 고정된 목표로 사용한다.

| ID | 완료 조건 |
|---|---|
| G01 | 기존 Reference 계산 방식이 유지됨 |
| G02 | 모든 유효 격자의 물리 상태가 지속적으로 계산됨 |
| G03 | 위험도 기반 임의의 수평 유동 계산 제외 정책이 제거됨 |
| G04 | 강우 입력의 순차 처리 및 처리 완료 후 폐기 정책이 구현됨 |
| G05 | Decaying Window가 명확한 목적에 따라 활용됨 |
| G06 | 지역별 적응형 계산 주기가 실제로 작동함 |
| G07 | 서로 다른 계산 주기의 지역 사이에서 질량 보존 및 수치 안정성이 확보됨 |
| G08 | 기존 OpenMP 병렬 처리와 CPU 스레드 설정이 정상적으로 작동함 |
| G09 | 10분 단위로 모든 지역의 수심 결과가 저장됨 |
| G10 | 대시보드에서 실제 계산 주기, 수심 및 성능 비교를 확인할 수 있음 |
| G11 | 기존 실행 제어 및 결과 조회 기능이 정상적으로 작동함 |
| G12 | 동일 자원의 Reference와 개선 방식에 대한 실제 성능 및 오차 측정 결과가 존재함 |
| G13 | README가 고정된 구조와 작성 규칙을 준수함 |
| G14 | 아키텍처 이미지와 관련 문서가 실제 구현과 일치함 |
| G15 | 기존 Windows 및 WSL 실행 방식이 유지됨 |
| G16 | 기존 원본 데이터와 저장된 결과가 보존됨 |

모든 완료 조건은 실제 코드 또는 확인된 실행 결과를 근거로 판단한다.

성능 향상이 확인되지 않았거나 정확성에 문제가 있는 경우 이를 숨기지 않는다. 단순히 알고리즘을 실행할 수 있다는 이유로 프로젝트의 개선 목적을 달성했다고 주장하지 않는다.

완료 조건을 변경하거나 일부를 삭제하여 DONE 상태를 만들지 않는다.

핵심 알고리즘이 구현되지 않았다면 나머지 기능이 정상적으로 작동하더라도 전체 작업을 완료로 선언하지 않는다.

## 15. 실행 종료 조건

자율 개발 루프는 다음 상태를 구분한다.

### DONE

모든 필수 완료 조건이 충족되었으며, 필요한 최종 검증을 마쳤다.

추가적인 개선 과제를 생성하지 않고 종료한다.

### CONTINUE

필수 완료 조건 중 해결되지 않은 작업이 남아 있으며, 현재 승인된 범위 안에서 해결할 수 있다.

다음 라운드에서는 남은 요구사항에 직접 연결되는 작업만 수행한다.

### BLOCKED

다음과 같은 문제가 발생한 경우다.

- 물리 엔진의 구조와 새로운 알고리즘이 근본적으로 충돌함
- 사용자에게 위임받지 않은 설계 변경이 필요함
- 필요한 데이터 또는 실행 환경이 존재하지 않음
- 정확성과 안정성을 확보할 수 있는 방법이 확인되지 않음
- 실제 사용 가능한 검증 환경이 부족함

작동하는 기존 구현을 보존하고, 문제와 필요한 사용자 판단을 명확하게 보고한다.

### FAILED

현재 라운드가 실행 오류 등으로 정상적으로 완료되지 못한 상태다.

기존 컨트롤러의 재시도 정책 범위 안에서만 재시도한다.

동일한 실패를 해결하지 못한 상태에서 무한 반복하지 않는다.

시간 제한 또는 최대 라운드 제한에 도달한 경우에도 DONE으로 처리하지 않는다. 실제 미완료 상태와 체크포인트를 보존한다.

## 16. 최종 작업 보고

작업 종료 시 사용자가 코드 전체를 읽지 않고도 결과를 판단할 수 있도록 다음 내용을 간결하게 보고한다.

### 변경 내용

기존 프로젝트의 무엇이 어떻게 달라졌는지 설명한다.

### 최종 적용 알고리즘

실제로 사용한 빅데이터 개념과 적용 위치를 정리한다.

### 성능 및 정확성

실제로 측정한 수치만 제공한다.

비교 조건, 계산 시간, 계산량 감소율, RMSE, IoU 및 주요 한계를 명시한다.

### 사용자 인터페이스

대시보드에서 새롭게 확인하거나 조작할 수 있는 내용을 설명한다.

### 검증 결과

실제로 확인한 동작과 확인하지 못한 동작을 구분한다.

실행하지 않은 검증을 성공했다고 작성하지 않는다.

### 남아 있는 문제

미해결 문제가 있다면 숨기지 않고 보고한다.

문제가 없다면 억지로 후속 개선 과제를 만들어 내지 않는다.

### 실행 방법

사용자가 기존 방식으로 프로젝트를 실행하고 결과를 확인할 수 있도록 안내한다.

## 17. 최종 행동 원칙

이번 작업에서 가장 중요한 것은 구현의 양이 아니라 사용자 의도와 결과의 일치다.

새로운 작업을 선정하기 전에 해당 작업이 고정된 완료 조건 중 무엇을 해결하는지 확인한다.

기존 시스템으로 해결할 수 있다면 재사용한다.

필요한 기능부터 구현한다.

검증은 구현 결과를 확인하는 데 필요한 만큼만 수행한다.

문서에는 실제로 구현한 내용을 작성한다.

대시보드는 실제 데이터와 계산 결과를 가장 직관적으로 보여주도록 유지한다.

프로젝트의 목적과 직접 관련되지 않는 기능을 개발하지 않는다.

문제가 발생하면 스스로 해결하되, 해결 과정에서 사용자의 목표를 변경하지 않는다.

**Build what matters. Remove what does not. Verify what must work. Stop when the goal is met.**
